## 1. プロダクトの目的と背景

### 主目的
**「終の棲家を探す旅」を支える、個人用の物件情報収集・整理・比較アプリ**を作る。

ユーザーは、すぐに転居することを前提にしていない。各地を訪れ、街の雰囲気や生活環境を見ながら不動産店にも気軽に立ち寄り、店主・担当者との対話も楽しみ、気になった賃貸物件の募集図面（マイソク）や関連情報を集めていく。集めた情報を蓄積し、時間をかけて地域・物件を比較し、自分に合う暮らしと場所を見極める。

したがって、このアプリは「今すぐ契約する物件を探す検索サイト」でも「不動産会社向けの市場賃料査定システム」でもない。**旅先で見つけた住まいの候補を、後から思い出し、整理し、比較できる自分専用の道具**である。

### 利用シーン
1. 訪問先の街を歩き、生活環境や交通、買い物、医療機関などを観察する。
2. 不動産店でマイソクを受け取り、店主や担当者から地域・物件の話を聞く。
3. マイソクや関連資料をスマートフォンで撮影し、その場で保存する。
4. 物件名や場所が未整理でも、まず画像と訪問時のメモを残す。
5. 後日、物件情報を補完し、複数地域・複数物件を比較する。
6. すぐに決断せず、時間をかけて候補や地域への理解を深める。

### 将来の可能性（初期スコープ外）
不動産店の店主に試作品を見せ、反応や要望を聞く機会はあり得る。将来、第三者向けの業務ツールとして展開する可能性も否定しない。ただし、現時点では事業化・販売・顧客管理・不動産会社向け査定機能を開発目的に含めない。まず本人が旅先で実際に使い、役立つことを最優先する。将来の業務用途は、実利用から具体的な要望が生まれた段階で別途検討する。

## 2. 設計の原則・絶対条件

- 初期運用費ゼロを原則とする。
- 従量課金API、有料AIフォールバック、無断の有料サービスを導入しない。
- 「少額だから許容」と判断しない。費用の発生可能性・上限・停止条件を明示し、本人の明示承認なしに課金を有効化しない。
- 無料枠の上限・利用条件を確認できないサービスは採用しない。
- 無料枠を超えた場合はAI解析を停止し、理由を表示する。別サービスへ勝手に切り替えない。
- AIが使えなくても、撮影・保存・手入力・メモ・整理・比較は利用できる。
- 現行mainを壊さず、別ブランチ・別プレビューで開発する。
- 実機検証前に本番を切り替えない。
- 事実、ユーザーの所感、AIによる読み取り・提案、未確認情報を明確に区別する。
- 不明な情報をAIが推測で補完しない。未確認のまま保持できること。

## 3. 現行版の棚卸しで確認したこと

- 現行UIは大きな単一の index.html に画面・状態・評価ロジック・画像処理・保存処理が集中している。
- Cloudflare Pages Functions の functions/api/analyze.js がGemini APIを呼び出す。
- Geminiモデル一覧の取得に失敗した際の候補名に、API一覧で実在・利用可能と確認できていない固定モデル名を混在させている。
- 429時にモデルを連続試行する実装がある。無料枠のプロジェクト制限に対して有効とは限らず、無駄なリクエストを増やし得る。
- 画像保存UIにはIndexedDB利用の記述があり、撮影・読込処理から保存関数を呼んでいる。
- 保存データはIndexedDBの folders object store に、folderNameを持つ画像レコードとして格納される。OSの実フォルダではない。
- 画像保存とAI解析は現行コード上で同じ画像取込フローに連続している。2.0では責務を分離する。
- 4桁ルーム同期はBroadcastChannelとlocalStorageを使う同一ブラウザ内の仕組みであり、端末間・クラウド同期とは限らない。
- 現行版には物件評価項目、沿線・駅条件、比較ボード、内見チェック、契約チェック、サンプル物件が含まれる。
- 現行版の評価項目には生活利便性・予算・駅アクセス等が含まれる。2.0では本人の長期的な住まい選びに役立つ要素として棚卸しし、使い勝手を確認してから移植する。数値や重みを無条件に引き継がない。

## 4. 2.0の機能要件

### A. 旅・地域・訪問記録
- 訪問した地域・街を記録できる。
- 訪問日、地域名、駅・エリア、街の印象、生活利便性、交通、買い物、医療機関、その他の気づきをメモできる。
- 物件情報をまだ入手していない街も、訪問記録として保存できる。
- 地域の記録と物件の記録を相互に関連付けられる。
- 訪問順・地域別に後から振り返れる。
- 地域評価は点数だけに固定せず、自由記述・写真・気づきを残せる。

### B. 物件管理
- 物件を新規作成できる。
- 物件ごとに物件名（仮称可）、所在地、地域・訪問記録との関連、登録日時、入手元（不動産店名・担当者名は任意）、メモ、検討状態を持つ。
- 物件名・住所が不明でも「未整理」として先に保存できる。
- 物件の編集・削除・アーカイブができる。
- 複数物件を一覧・検索・地域別表示・比較できる。
- 不動産店との会話内容は、個人情報を必要以上に集めず、物件選びに役立つ要点を自由メモとして記録できる。
- 「検討中」「保留」「候補外」などの状態は、急いで決断させない表現にする。

### C. 撮影・画像管理
- Pixel 8aのブラウザからカメラ撮影または既存画像を読み込める。
- 画像取込直後、AI処理より先に原画像をIndexedDBへ保存する。
- 保存成功・失敗を画面に明示する。保存失敗時はAI解析へ進む前にユーザーへ警告する。
- 1物件に複数画像をひも付けられる。マイソク、間取り図、周辺地図、店頭掲示、その他資料を区別できる。
- まだ物件に紐付けられない画像は「未整理資料」として一時保存し、後から物件へ紐付けられる。
- 原画像と解析用派生画像を別管理する。
- 画像のプレビュー、削除、再解析、端末へのダウンロードができる。
- ブラウザ内保存であり、OSファイルアプリやクラウドに自動同期されないことを明示する。
- 容量不足、プライベートブラウズ、ストレージ拒否時の挙動を設計する。
- JSONメタデータ＋画像一括エクスポート／インポートを用意し、端末変更・ブラウザデータ消去への備えとする。
- 画像ファイルの実フォルダをOS内に自動作成するかのような表示・説明をしない。アプリ内の分類と端末のファイル管理を区別する。

### D. マイソク情報の読み取り・その場での即時分析
- 今年初め頃にGeminiのGemで運用していた「不動産店で提示されたマイソクをその場で撮影し、内容を読み取り、希望条件と照合して分析・採点する」体験を、2.0でも中核機能として引き継ぐ。
- 現地では、撮影 → 原画像保存 → 情報読み取り → 希望条件との照合 → 評価・採点、までを短い操作で行えることを目指す。
- 即時分析は必須の利用シーンだが、AI解析は任意機能として扱い、画像保存の成功を先に確定する。AIが利用できない場合も、保存と手入力は続けられる。
- 即時分析の結果は暫定評価として表示し、帰宅後に情報を修正・補完して再評価できる。
- その場での分析結果と、後日蓄積した複数物件・複数地域の比較結果を同じ物件データに紐付ける。
- 解析対象は原画像そのものではなく、読みやすさを保つ範囲で最適化した派生画像。
- 抽出項目候補：物件名、所在地、賃料、管理費・共益費、敷金、礼金、最寄駅、徒歩分数、間取り、専有面積、築年月／築年、構造、所在階、総階数、設備、備考。
- 各項目は値だけでなく source（AI読取／手入力／未確認）と必要に応じ confidence を保持する。
- 読み取れない項目は null／未確認とし、推測で埋めない。
- AI読取値を既存の手入力値で無断上書きしない。差分確認後に採用する。
- OCR結果は原本画像と照合するよう促す。
- マイソクの記載と、不動産店で聞いた口頭情報・ユーザー自身の現地観察を別の情報源として保存する。

### E. 評価・比較
- 評価エンジンはAIから独立したローカルJavaScriptで実行する。
- ユーザーが設定した評価項目・重み・必須条件を保存できる。
- 住居費だけでなく、交通、買い物、医療、周辺環境、建物・設備、間取り、管理状態、街との相性などを比較できる。
- 評価項目は後から追加・変更でき、ユーザーの判断軸を固定しない。
- 点数化が難しい印象や店主との会話、街の雰囲気は自由メモとして残せる。
- AIが自動で最終評価や契約判断を決定しない。
- 物件情報の事実、ユーザーの評価、AIのコメントを別領域で表示する。
- 未確認情報が多い物件は、その不確実性をスコアと同時に表示する。
- 現行版の沿線・生活利便性・予算・内見・契約チェックの知見は棚卸しして移植候補とする。数値や重みはユーザー確認なしに固定しない。
- すぐに引っ越す前提の期限・決断圧力・申込誘導をUIの中心に置かない。

### F. AI解析のコスト・障害制御
- Gemini APIは無料枠での利用条件が確認できる場合のみ任意機能として採用する。
- 実在モデル名を推測でハードコードしない。Google公式のモデル一覧・対応メソッドを事前検証する。
- 429を受けたら同一リクエストでモデルを次々試さず、原則停止する。RetryInfo等の明示情報を表示する。
- APIキーはCloudflare環境変数に保持し、フロントエンドへ露出させない。
- 画像サイズ・送信回数に上限を設け、二重送信を防ぐ。
- 無料枠の利用条件やモデル提供条件が変わった場合に、無料前提が崩れないよう運用前に再確認する。
- 従量課金の可能性がある別AIサービスへのフォールバックは禁止。
- AI解析の利用状況・失敗理由をユーザーに分かる形で表示する。解析できない場合も保存・整理作業は続けられる。

## 5. 非機能要件

- Pixel 8aのChromeで片手操作しやすい。
- 旅先で短時間に「撮影して保存」できることを最優先する。
- 撮影時に物件名や詳細情報の入力を強制しない。
- 通信が不安定でもローカルの地域・物件・画像・メモにアクセスできる。
- AI解析失敗で入力中データや画像が失われない。
- データの削除・エクスポート方法が明確。
- UIは日本語。撮影・保存・解析の状態を明確にする。
- 依存ライブラリは必要最小限。静的フロントエンド＋Cloudflare Pages Functionsを基本候補とする。
- スマートフォンを主画面とし、PCでは地域横断・物件横断の比較と整理をしやすくする。

## 6. 推奨アーキテクチャ案

- Frontend: HTML/CSS/JavaScriptを機能別モジュールに分割。
- Storage: IndexedDB。地域・訪問記録、物件、画像、評価設定、チェック項目を別object storeで管理。
- Data relationship: 地域／訪問記録 → 物件 → 資料画像・メモ。未整理画像は後から物件へ関連付け可能にする。
- Image pipeline: 原画像保存 → 派生画像生成 → 任意でAI解析。
- AI endpoint: Cloudflare Pages Functions。無料枠確認済みのGemini呼び出しのみ。AIがなくてもアプリの他機能は動く。
- Evaluation: ブラウザ内の決定的なルールエンジン。AI出力を評価点へ直結させない。
- Backup: JSON＋画像のエクスポート／インポート。
- Deployment: maisoku-v2-rebuildブランチでPreviewを検証し、合格後に別途切替判断。

10. 契約チェック（必要なときに利用）

スマートフォンでは撮影・保存・メモを最短手順にし、PCでは一覧・比較・振り返りを重視する。

- 4桁ルームコードによる複数端末同期を2.0にも必要とするか。現行方式は同一ブラウザ内のタブ間同期であり、端末間同期ではない。
- データをPixel端末内だけに保存するか、PCへの手動エクスポートを標準にするか。

- AI解析はGemini無料枠が使える場合のみ搭載するか、まず手入力・保存・比較を完成させてから追加するか。
- 地域の生活情報を手入力中心にするか、将来、無料で安定した公的データ等を参照する機能を設けるか。外部サービス連携は費用・規約・継続性を確認してから判断する。

## 10. 合格基準

- AI APIを使わなくても、地域記録・物件登録・画像保存・編集・比較ができる。
- 旅先で撮影した原画像を、物件名等を入力せず「未整理資料」として先に保存できる。
- 後から画像を地域・物件へ紐付けられる。
- 撮影した原画像が確実に保存され、ページ再読込後も残る。
- 物件ごとに複数画像を保存・表示・削除できる。
- 保存容量不足などを隠さず通知する。
- エクスポートしたデータをインポートして復元できる。
- AI解析が失敗しても、物件・画像・入力情報が失われない。
- 不動産店で聞いた情報とマイソク記載、本人の所感を区別して記録できる。
- 地域・物件を横断して比較できる。
- 有料サービスへの自動移行が存在しない。
- Pixel 8aで一連の操作を実機確認する。
- Previewと本番の反映状態を別々に記録する。

## 11. Geminiから引き継ぐ評価資産（統合候補・配点未確定）

この章は、旧Gemini Gemで使われていた評価項目・チェック項目を2.0へ引き継ぐための整理である。ここに記載した項目は引き継ぎ候補であり、重み・必須条件・点数計算式はユーザー確認前に確定しない。

### 11-1. 基本スペックの入力・抽出項目

- 物件名・所在地
- 賃料、管理費・共益費、月額総額
- 最寄駅、沿線、駅徒歩分数
- 築年数、所在階、建物の総階数
- 間取り、専有面積（㎡）

### 11-2. 基本条件チェック（旧Gemの6項目）

各項目を個別に確認できるトグル／チェックとして扱う。

1. RC／SRC造
2. エレベーター
3. 室内洗濯機置き場
4. 風呂・トイレ別
5. 整形間取り
6. 収納奥行き

これらを一律に失格条件とするか、希望条件・妥協可能条件として扱うかは未確定。ユーザーが項目ごとに「必須」「できれば欲しい」「妥協可能」等を設定できる方向を検討する。

### 11-3. 評価マトリクス候補

旧Gemでは各項目を「〇（良）／△（普通・要確認）／×（不利・要調整）」で評価し、重み x1〜x3 を掛ける方式が使われていた。2.0では、まずこの評価表現とカテゴリを引き継ぎ、数値化・合計点・重みの初期値は実例確認後に決める。

| ランニングコスト | 賃料＋管理費の予算適合度、都市ガス／プロパンと光熱費水準、更新料・更新事務手数料・火災保険料 | x2〜x3 |

| 要確認ポイント | 短期解約違約金（1年・2年未満等）、退去時クリーニング代・原状回復特約、駐輪・生活ルール・管理規約上の制限 | x2 |

### 11-4. 沿線・立地の補正観点

- 停車種別だけで機械的に評価せず、複数路線の結節点、近隣の別路線へのアクセス、乗換選択肢を合わせて評価する。
- 普通停車駅でも、結節点や別路線への移動が容易なら迂回ルート・選択肢の多さをプラス要素として扱える。
- 単一路線・普通停車・主要地点から遠い条件が重なる場合は、アクセス面の確認事項として示す。
- 下町、商店街、市街地、平地、坂の多い地域、郊外など、街の性格・地形を記録し、自転車移動や日常の買い物との相性を評価する。
- 沿線の停車種別・所要時間・施設の営業状況など変化し得る情報は、確認日時と情報源を記録する。AIの一般知識だけで現在の状況を確定しない。

### 11-5. 未記載情報から生成する確認質問

AIは募集図面に記載されていない情報を事実として補完しない。既知の情報から「確認した方がよい点」と「不動産店への質問フレーズ」を生成する。

例：
- 築年数が古い場合：給湯器・水回り・配管・共用設備の更新履歴を確認する。
- 最上階の場合：夏季の日射熱、屋根からの熱、断熱・空調効率を確認する。
- 賃料と専有面積から㎡単価・坪単価の参考値を計算する。単価だけで割安・割高と断定せず、地域・築年・設備等との比較材料として扱う。
- 設備の年式や電気容量が不明な場合：型番・製造年・契約アンペア等の確認を促す。

推察には必ず「AIによる確認提案」等のラベルを付け、募集図面の記載・担当者から聞いた情報・現地で確認した事実と混同させない。

### 11-6. 内見チェック項目

- スマートフォンの4G／5G通信の室内での入り具合
- 窓を閉めた状態・開けた状態それぞれの道路・鉄道・周辺騒音
- キッチン・洗面・浴室・洗濯機パンの排水、臭い、水勢、給湯温度
- 壁・天井・サッシ周辺のシミ、結露、カビ跡
- デスク、冷蔵庫、電子レンジ、洗濯機周り等のコンセント位置・数
- エントランス、廊下、階段、駐輪場、ゴミ置き場等の共用部管理状態
- 駅からの実際の歩きやすさ、街灯、坂、スーパーまでの生活導線

チェック結果は「確認済み／問題あり／未確認／対象外」等で記録し、写真・メモを添付できるようにする。

### 11-7. 契約時チェック項目

- 賃料＋管理費・共益費＋駐輪場代等の月額総支払額と募集図面の一致
- 敷金、礼金、前家賃、保証会社初回料、仲介手数料、鍵交換費等の初期費用明細と不要オプションの有無
- 短期解約違約金の適用期間と金額
- 退去時精算、ハウスクリーニング特約、エアコン清掃費の負担範囲
- 更新料、更新事務手数料、保証会社更新料、引落手数料
- 重要事項説明書（宅地建物取引業法第35条に基づく書面）の事前確認と不明点の解消

このチェックリストは将来、実際に契約を検討する段階で使うものとし、通常の旅先での物件収集時に入力を強制しない。

### 11-8. データの情報源・修正履歴

物件情報の各フィールドについて、少なくとも以下を区別する。

- AI読取値
- ユーザーの手入力・修正値
- マイソク等の原資料に明記された値
- 不動産店・担当者から口頭で聞いた情報
- ユーザー自身が現地・内見で確認した情報
- 未確認

AI読取値と手入力値を同一フィールド上で無条件に上書きしない。手入力値を優先して保持し、再解析で値に差異が出た場合は差分を提示してユーザーが選べるようにする。元画像と登録・修正日時を追跡可能にする。

### 11-9. 商談提示モードの扱い

内部メモや要注意フラグを第三者に見せる際の表示整理（商談提示モード）は、Gemini資料に含まれていた将来案として記録する。ただし、現在の主目的は本人専用の住まい探しであるため、初期開発の対象には含めない。実利用後に第三者へ提示する具体的な必要性が生じた場合に再検討する。

### 11-10. 評価結果の表示原則

- 〇／△／×の評価と、x1〜x3の重みは、旧Gemの考え方を再現する候補として保持する。
- 未確認項目を「×」扱いにしない。未確認は未確認として表示し、評価の確度と確認優先度を別に示す。
- ハードフィルター、希望条件、妥協可能条件を区別する。
- 合計点だけで結論を出さず、評価理由・不利な点・未確認事項・次に聞く質問を併記する。
- 評価項目・重み・必須条件は、実際の旧Gem指示文とユーザーの確認を経て確定する。


## 12. 住居費の公的基準を参考にしたプライバシー配慮型チェック

### 12-1. 目的

住まい候補の比較にあたり、地域ごとの公的な住居費基準や生活費の考え方を参考情報として利用し、家賃が日々の生活を圧迫しないかを確認できるようにする。特定の制度の利用・申請・受給資格を判定する機能ではなく、本人の住居費計画を考えるための参考指標とする。

### 12-2. 画面表示と内部ルールの分離

- 画面上の標準ラベルに「生活保護」「受給」「保護基準」等の表現を出さない。
- ユーザー向け表示名の候補は「住居費の目安」「地域別住居費基準」「毎月の生活余力」「住居費バランス」等とする。
- 制度上の根拠・参照元・計算ロジックは、設定・ヘルプ等の詳細情報に明示し、必要な場合に本人が確認できるようにする。制度名を完全に隠して出典を偽装する設計にはしない。
- 設定項目は任意とし、初期画面で個人的な制度利用状況を質問しない。本人が希望した場合に限り、世帯構成等の計算条件を設定できる。
- 物件一覧・比較画面では制度名や個人属性を表示せず、「参考目安内」「目安を超過」「条件未設定」等の中立的な表示を使う。
- 計算結果は物件の優劣を自動決定する点数に直結させず、住居費に関する独立した確認指標として表示する。

### 12-3. 参照データと限界

- 住宅扶助等の公的基準は地域、世帯構成、適用条件等により異なる。全国一律の家賃上限として扱わない。
- 基準額は改定されるため、数値をコードへ固定せず、適用開始日・対象地域・世帯条件・出典URL・確認日を持つデータとして管理する。
- 初期実装では、公式資料から確認できた地域別の参考値を登録する場合も、出典と適用時点を必ず併記する。公式情報を確認できない地域・条件は「データ未確認」とする。
- 住宅扶助の基準額は個別事情や特例等の影響を受け得るため、アプリの参考値を行政上の認定額・受給可能額と同一視しない。
- 生活保護の要否や受給資格、保護費総額を自動判定しない。正確な確認が必要な場合は自治体の福祉事務所等への確認を案内する。
- 家賃だけでなく、管理費・共益費、駐輪場代、光熱費、更新料等も含めた実際の住居関連支出を別途表示する。公的な住宅扶助基準と、本人の実支出・生活余力を混同しない。

### 12-4. 表示例

- 「住居費の参考目安：範囲内／目安超過／未確認」
- 「月額住居費：○円（賃料・管理費・共益費・駐輪場代を含む）」
- 「参考目安との差：＋／−○円」
- 「この目安は公的資料を参考にした比較情報です。個別の適用可否や支給額を判定するものではありません。」

制度名を前面に出さずとも、数字の根拠と限界は詳細表示で確認可能にする。

## 13. 内見・契約チェックリストの画面要件

### 13-1. 物件詳細からいつでも参照可能

- 物件詳細画面に「基本情報」「評価」「内見チェック」「契約チェック」「メモ・資料」の切替を設ける。
- 内見・契約チェックは物件ごとに保存し、別物件へ誤って混在させない。
- チェックリストは折りたたみ可能にし、必要なときだけ展開できる。
- 旅先で物件を集めている段階では、内見・契約チェックの入力を要求しない。
- 物件の検討状態に応じて、必要なチェック項目への入口を提示するが、ユーザーの操作なしに契約段階へ進めない。

### 13-2. 内見チェックの操作

- 各項目を「未確認」「問題なし」「要確認・問題あり」「対象外」から選択できる。
- コメント、写真、確認日を項目ごとに追加できる。
- 「要確認・問題あり」の項目は一覧で見返せる。
- 未確認項目を問題なしとして集計しない。
- チェックリスト全体の進捗（例：確認済み／全項目）を表示する。

### 13-3. 契約チェックの操作

- 初期費用、月額費用、更新・解約条件、退去時費用、重要事項説明の各グループに分ける。
- 金額・期間・契約書の該当箇所のメモや写真を保存できる。
- 募集図面・口頭説明・見積書・契約書の内容が異なる場合、差異を記録できる。
- 不明点が残っている項目を契約前の確認事項として一覧表示する。
- 法律判断や契約の有効性をAIが断定しない。必要に応じて宅地建物取引士、自治体、専門家等への確認を促す。

### 13-4. 画面上の優先順位

- 撮影・保存・物件の基本情報を最短操作で行えることを最優先とする。
- 内見・契約チェックは必要な段階で開ける独立機能とし、初期画面をチェック項目で埋めない。
- PCではチェック状況と未確認事項を一覧しやすくし、スマートフォンでは現場で片手入力しやすくする。


## 14. 地域別の住居費基準・長期的な住居費持続性（2026-11-25調査反映）

### 14-1. この機能の位置づけ

- 住宅扶助の地域別上限は、本人の現在の受給資格や利用予定を示すものではなく、将来の住まいの選択肢を考えるための「制度上の参考目安」として扱う。
- 通常画面では「住居費の参考目安」「地域別住居費基準」「住居費バランス」等の中立的な表現を用いる。
- 詳細画面・出典欄では、参照している制度名、根拠資料、適用年月、確認日を正確に開示する。制度名を隠して別制度の数値であるかのように見せない。
- 公的基準の比較と、本人が現実に支払えるかの家計シミュレーションは、別々の指標・別々の計算として実装する。
- 資産・収入・制度利用状況などの個人情報は初期設定で要求しない。本人が明示的に希望した場合に限り、必要最小限の入力を任意で受け付ける。
- 本機能は生活保護の要否・受給資格・支給額、住居確保給付金の受給資格を判定しない。行政判断の代替にしない。

### 14-3. 上限の適用条件・注意事項

- 住宅扶助の参考上限の対象は原則として家賃であり、管理費・共益費・駐車場代等は含めない。アプリでは家賃と管理費等を別フィールドで保持し、月額実負担では合算する。
- 単身世帯で専有面積15㎡以下の場合、面積区分に応じた限度額の減額があり得る。
- 2026年11月25日時点の調査で具体的な面積別金額まで確認できたのは大阪市の例（15㎡超40,000円、11〜15㎡36,000円、7〜10㎡32,000円、6㎡以下28,000円）。他の5市は制度適用の可能性を示すにとどめ、具体額を推測計算しない。
- 面積別減額の例外・特別基準・経過措置等があり得るため、アプリは通常ルールの参考表示に限定する。
- 家賃が参考上限を超えた場合に「超過分を払えば居住可能」「自己負担で継続できる」と断定しない。実際の取扱いは福祉事務所の判断・個別状況による。
- 特別基準（例：通常限度額の1.3倍の範囲）等は複雑な個別認定を伴うため、初期版で自動適用額を算出しない。
- 参考上限内であっても、管理費・共益費・光熱費・更新料等を含む生活上の負担が軽いとは限らない。

### 14-4. 物件ごとの計算・表示

物件ごとに以下を別々に保持・表示する。

1. 家賃（月額）
2. 管理費・共益費（月額）
3. 駐輪場代・駐車場代等（月額）
4. 月額住居費合計（上記の合計）
5. 地域別の公的参考上限（該当データがある場合）
6. 家賃と参考上限との差額
7. 参考上限データの確認状態（公式確認／間接確認／未確認）
8. 面積条件による補正の有無（補正額が未確認なら「金額未確認」）
9. 参照元・適用年月・確認日

表示例：
- 「家賃：39,000円」
- 「管理費等：4,000円」
- 「月額住居費：43,000円」
- 「地域別の参考目安：40,000円（調査時点・単身・家賃のみ）」
- 「家賃との差：−1,000円」
- 「管理費等は参考上限の対象外。月額住居費とは別に確認してください」
- 「この値は参考情報です。個別の認定額・支給額を示すものではありません」

表示状態は少なくとも「参考目安内」「参考目安超過」「条件未設定」「データ未確認」「間接確認・要再確認」を区別する。未確認・確度の低い値を、確定値と同じ色・表現で表示しない。

### 14-5. 住居費の持続可能性（本人の家計）との分離

- 公的参考上限とは別に、本人が任意で設定する「月額住居費の予算」または「住居費を支払った後に残したい金額」を用いて、家計上の負担を比較できるようにする。
- 収入・資産・制度利用状況の入力は必須にしない。本人が設定した予算額だけで簡易比較できる。
- 家賃だけでなく、管理費・共益費、駐輪場代、光熱費、更新料（月割り参考額）等を含めるかどうかを明示し、含めた費目を一覧表示する。
- 本人が月額予算を設定していない場合は、負担の軽重を勝手に判定せず「予算未設定」とする。
- 「公的参考目安内」と「本人の予算内」は別の状態として表示する。片方を満たしても、もう片方を満たすとは限らない。
- 株式・預貯金等の資産額をアプリが推定・取得しない。個人の資産情報を住居費評価へ自動投入しない。

### 14-6. 将来見通しの扱い

- 2015年7月適用の限度額が2026年11月時点でも継続していること、住宅扶助上限に家賃・物価への自動連動や法定の定期改定サイクルが確認できないことを、調査時点の背景情報として記録する。
- 2026年11月25日時点で住宅扶助上限の引き上げは決定していない。生活扶助本体の2027年10月改定予定と、住宅扶助の改定を混同しない。
- 将来シナリオは「据え置き」「引き上げ」「制度・算定方法の変更」等の仮説として表示し、実施時期・改定率を確定予測しない。
- 仮に1割改定などの試算を行う場合は、ユーザーが条件を指定したシミュレーションとして扱い、政府方針・公式予測のように表示しない。
- 家賃相場の上昇率等の二次資料は、原統計未照合であること・対象地域・対象期間を併記し、住宅扶助上限の自動改定率へ転用しない。
- 制度改定のニュースや公式資料を将来取り込む場合、資料日付・公表主体・確定／検討中／報道／推測の区分を保存する。

### 14-7. 出典・更新・確度のデータ構造

公的基準データは、少なくとも以下を保持する。

- region_id / 地域名
- household_type（単身等）
- amount_yen（月額上限）
- covered_cost（家賃のみ等）
- floor_area_rule（面積区分・減額条件。未確認はnull）
- effective_from / effective_to
- source_type（国通知／自治体公式／議会記録／二次資料等）
- source_url
- checked_at
- confidence（公式直接確認／公式制度資料からの対応確認／間接確認／未確認）
- notes（例外・未確認事項・再確認が必要な点）

基準データの更新時は旧値を上書きせず、適用期間を持つ履歴として保存する。データの確認日と制度の適用開始日を混同しない。根拠資料が失効・更新された場合は旧データを「過去の参考値」として残し、現行値と区別する。
